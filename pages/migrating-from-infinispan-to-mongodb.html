Migrating from Infinispan to MongoDB: A Transparent Evolution

In enterprise applications, infrastructure modernization often becomes necessary as systems grow and encounter scaling challenges. However, rewriting application code during such migrations can introduce risks and delays. This article describes how we successfully migrated from an Infinispan+RocksDB+Lucene stack to MongoDB Atlas while preserving our application's interface contracts.

The Legacy Architecture: Infinispan + RocksDB + Lucene

Our original architecture consisted of three main components:

  • Infinispan: An in-memory data grid providing caching capabilities
  • RocksDB: A persistent key-value store acting as Infinispan's backing storage
  • Lucene: A search engine library for indexing and querying data

This architecture had served us well initially, offering both in-memory performance and persistence. Our application code interacted with these components primarily through two abstractions:

  1. The org.infinispan.Cache interface for CRUD operations
  2. Hibernate Search QueryBuilder for search operations

The Growing Challenges

As our system scaled, several issues emerged:

  • Transaction Fragility: Transactions weren't properly coordinated between the storage layer (RocksDB) and the indexing layer (Lucene)
  • Memory Pressure: Infinispan's in-memory design consumed significant JVM heap space
  • Resource Contention: RocksDB operations ran in the same JVM, competing for CPU and memory resources
  • Operational Complexity: Manual management of storage and compute resources became increasingly difficult
  • Cluster Stability: The open-source version of Infinispan's clustering capabilities proved unreliable at scale

Why MongoDB Atlas?

MongoDB Atlas offered several advantages that addressed our pain points:

  • Managed Service: Infrastructure management handled by the provider
  • Separation of Concerns: Database operations run outside application JVM
  • Scalability: Horizontal scaling capabilities without application changes
  • ACID Transactions: Document-level atomic operations with transaction support
  • Query Capabilities: Rich query language that could replace our Lucene queries

The Migration Strategy

Our key insight was to implement the org.infinispan.Cache interface on top of MongoDB. This approach allowed us to:

  • Change the underlying infrastructure
  • Preserve all application code
  • Avoid modifying business logic
  • Focus testing on the adapter layer

Implementation: The MongoDB Cache Adapter

Here's how we implemented the Infinispan Cache interface using MongoDB:

public class MongoCache<K, V extends ResourceEntity> implements Cache<K, V> {

    private final MongoCollection<V> db;
    private final Map<Object, Tuple2<CacheEventFilter, Set<Class<? extends Annotation>>>> listeners = new ConcurrentHashMap<>();

    public MongoCache(MongoCollection<V> db) {
        this.db = db;
    }

    @Override
    public int size() {
        return (int) db.countDocuments();
    }

    @Override
    public boolean isEmpty() {
        return db.countDocuments() == 0;
    }

    @Override
    public boolean containsKey(Object key) {
        return db.countDocuments(Filters.eq("id", key)) != 0;
    }

    @Override
    public V get(Object key) {
        try(MongoCursor<V> it = db.find(Filters.eq("id", key)).iterator()) {
            if (it.hasNext()) {
                return it.next();
            } else {
                return null;
            }
        }
    }

    @Override
    public V putIfAbsent(K key, V value) {
        value.setMongoId(null);

        long count = db.countDocuments(Filters.eq("id", key));
        if (count == 1) {
            return value;
        } else if (count == 0) {
            db.insertOne(value);
        } else {
            throw new ServiceException(SC_MORE_THAN_ONE_RECORD_FOUND);
        }
        return value;
    }

    @Override
    public V put(K key, V value) {
        value.setMongoId(null);

        long count = db.countDocuments(Filters.eq("id", key));
        if (count == 1) {
            db.replaceOne(Filters.eq("id", key), value);
        } else if (count == 0) {
            db.insertOne(value);
        } else {
            throw new ServiceException(SC_MORE_THAN_ONE_RECORD_FOUND);
        }
        return value;
    }

    @Override
    public V remove(Object o) {
        try(MongoCursor<V> it = db.find(Filters.eq("id", o)).iterator()) {
            if (it.hasNext()) {
                V val = it.next();
                db.deleteOne(Filters.eq("id", o));
                return val;
            } else {
                return null;
            }
        }
    }

    // Listener management methods
    @Override
    public void removeListener(Object listener) {
        try {
            listeners.remove(listener);
        } catch (Exception ignored) {}
    }

    @Override
    public void addListener(Object listener) {
        listeners.put(listener, null);
    }
}

Key Implementation Considerations

Our adapter implementation addressed several important aspects:

  1. Document Mapping: We mapped cache keys to MongoDB document IDs
  2. CRUD Operations: Translating cache operations to equivalent MongoDB operations
  3. Consistency: Ensuring atomicity for operations like putIfAbsent
  4. Error Handling: Translating MongoDB exceptions to semantically equivalent cache exceptions
  5. Event Listeners: Maintaining a simplified event model for backward compatibility

Replacing Lucene with MongoDB Queries

We also needed to replace our Lucene-based search functionality. MongoDB's query capabilities proved suitable:

// Replacing Lucene queries with MongoDB queries
List<Bson> andFilters = new ArrayList<>();
andFilters.add(Filters.eq(name, value));

Bson query = Filters.and(andFilters);

MongoCollection<E> db = null; // inject instance
db.countDocuments(query)

We created adapter classes that accepted the same query parameters but constructed MongoDB queries instead of Lucene queries. This approach maintained the query interface while changing the implementation details.

MongoDB Configuration

Proper MongoDB configuration was crucial for success. Here's our configuration approach:

@Bean
public MongoDatabase mongoDatabase(MongoClient mongoClient,
                               Config config) throws ClassNotFoundException {

    List<Convention> DEFAULT_PLUS_NULL_EMPTY = unmodifiableList(asList(
            CLASS_AND_PROPERTY_CONVENTION,
            ANNOTATION_CONVENTION,
            OBJECT_ID_GENERATORS,
            new IgnoreNullEmptyConvention()
    ));

    PojoCodecProvider.Builder codecBuilder = PojoCodecProvider.builder().automatic(true);

    List<String> configClasses = config.getConfigList("repo.cache").stream()
            .map(val -> val.getString("valueClass"))
            .collect(Collectors.toList());
    configClasses.add("life.arogya.core.domain.fhir.type.CodeableConcept");
    configClasses.add("life.arogya.core.domain.fhir.type.Extension");

    for (String clazz : configClasses) {
        Class<?> entity = Class.forName(clazz);
        ClassModelBuilder modelBuilder = ClassModel.builder(entity);

        Arrays.stream(entity.getDeclaredMethods())
                .filter(m -> m.isAnnotationPresent(JsonIgnore.class))
                .forEach(method -> modelBuilder.removeProperty(attributeName(method)));

        Arrays.stream(entity.getDeclaredFields())
                .filter(field -> field.isAnnotationPresent(JsonIgnore.class) && !field.getName().equals("mongoId"))
                .forEach(field -> modelBuilder.removeProperty(field.getName()));

        codecBuilder.register(modelBuilder.conventions(DEFAULT_PLUS_NULL_EMPTY).build());
    }
    codecBuilder.register(new GenericTypeCodecProvider());

    CodecProvider pojoCodecProvider = codecBuilder.conventions(DEFAULT_PLUS_NULL_EMPTY).build();
    CodecRegistry pojoCodecRegistry = fromRegistries(getDefaultCodecRegistry(), fromProviders(pojoCodecProvider));

    CodecRegistry codecRegistry = CodecRegistries.fromRegistries(
            fromCodecs(new ResourceListCodec(pojoCodecRegistry)),
            pojoCodecRegistry
    );

    String database = config.getString("mongodb.name");
    return mongoClient.getDatabase(database).withCodecRegistry(codecRegistry);
}

Key Configuration Elements

  • POJO Codec Configuration: Enabling automatic mapping between Java objects and MongoDB documents
  • Custom Conventions: Handling null/empty values appropriately
  • Field Exclusion: Respecting JsonIgnore annotations for proper serialization
  • Custom Codec Registration: Supporting specialized types in our domain model

Key Insight: Interface Preservation

By preserving the Cache interface, we achieved a significant infrastructure migration with:

  • Zero changes to application business logic
  • Minimal regression risk
  • Phased migration capability
  • Lower testing burden

This approach demonstrates the power of programming to interfaces rather than implementations.

Lessons Learned

  1. Abstraction Boundaries Matter: Well-defined interfaces enabled infrastructure changes without application rewrites
  2. Testing Strategy: We could focus testing on the adapter layer rather than retesting all application logic
  3. Performance Characteristics: While the interface remained the same, performance characteristics changed (network calls vs. in-memory), requiring careful monitoring
  4. Documentation: Clear documentation of the original interfaces made reimplementation significantly easier
  5. Migration Path: We could migrate collections incrementally rather than requiring a "big bang" approach

Conclusion

Our migration from Infinispan+RocksDB+Lucene to MongoDB Atlas demonstrates how strategic use of interfaces and adapters can facilitate major infrastructure changes while preserving application integrity. By implementing the org.infinispan.Cache interface on top of MongoDB, we achieved a more scalable, manageable system without modifying our core application code.

This approach underscores a fundamental principle of software engineering: programming to interfaces creates flexibility that can pay dividends when infrastructure needs evolve. The separation of interface from implementation provided us with the freedom to make substantial backend changes while maintaining application stability.

For teams considering similar migrations, we recommend:

  • Identifying the key interfaces your application depends on
  • Creating targeted adapters that maintain those interfaces
  • Testing adapter implementations thoroughly
  • Planning for incremental migration rather than all-at-once changes

With careful planning and a focus on interface preservation, even significant infrastructure migrations can be achieved with minimal disruption to application code.
